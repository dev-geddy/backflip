- `L2-UI-25` — Admin chrome theming — the signed-in user's sidebar + header palette. The protected layout resolves it server-side and stamps `data-chrome-theme="<id>"` on the shell wrapper (`SidebarProvider`), so the themed chrome arrives with the server HTML and never flashes the default. CSS lives in `packages/ui/src/styles/globals.css`: per-theme blocks set `--sidebar-*` plus a `--chrome-header-*` family, and two scoped rules re-point the base tokens (`--foreground`, `--muted-foreground`, `--border`, `--accent`, …) inside `[data-slot="site-header"]` and `[data-slot="sidebar-inner"]` so existing children need no theme awareness. Page content is never tinted. (`apps/web/app/backflip/(protected)/layout.tsx`, `_components/site-header.tsx`, `account/_components/appearance-section.tsx`)
- `L2-UI-27` — `getChromePreferences(userId)` → `{ theme, headerThemed }`, plus `setChromeTheme` / `setChromeHeaderThemed` (`apps/web/app/_lib/theme/preferences.ts`) — server-only read/upsert over `user_preference` (`L2-DB-33`). A missing row means every default; nothing is seeded at signup.
- `L2-UI-32` — Header opt-out — `user_preference.chromeHeaderThemed` (`L2-DB-33`), surfaced as the "Tint the header too" switch. Off → the layout stamps `data-chrome-header="plain"`, whose CSS block points the `--chrome-header-*` tokens back at the stock palette; the sidebar stays themed and the header follows plain light/dark. Server action `saveChromeHeaderThemed(enabled)` (`account/_actions.ts`), self-scoped, revalidates the `/backflip` layout.
- `L2-UI-33` — Custom theme — id `custom`, stored as two `#rrggbb` colors in `user_preference` (`chromeCustomSurface`, `chromeCustomAccent`, `L2-DB-33`). It has **no** stylesheet block: `customChromeVars(surface, accent)` builds the same variable set a theme block declares and the layout emits it inline on the shell wrapper. Ink, border and ring are derived from the two picks (near-white or near-black by WCAG luminance, mixed with the surface to keep its hue), so no pick can be unreadable. Server action `saveCustomChrome(surface, accent)` validates both colors. Honours `L2-UI-32`: with the header plain the `--chrome-header-*` variables are omitted from the inline set rather than overridden — inline style outranks the opt-out rule. Rendered as a two-column card beside Default. (`chrome-themes.ts`, `account/_components/appearance-section.tsx`)
- `L2-UI-42` — Admin sidebar nav (`app-sidebar.tsx`) carries the **working surfaces** only: **Platform** (Overview → `/backflip`, cap `dashboard`) and a bottom-pinned **Settings** (Integrations → `/backflip/settings`, cap `settings`, icon `RiLinksLine`). Administrative destinations — Members (`/backflip/users`, cap `users.view`, icon `RiGroupLine`) and Account (`/backflip/account`) — live in the `NavUser` dropdown instead, so the rail stays short and the identity chip owns "who is here and who else is". Capabilities are unchanged and still gate both the menu item and the route; the Members item is hidden for a role without `users.view` (teammate), which is why `NavUser` imports `can`.
- `L2-UI-43` — Menu items in the `NavUser` dropdown carry `cursor-pointer`. The shared `DropdownMenuItem` ships `cursor-default` (native-menu convention); the sidebar user chip reads as a web control, so its items point like the ⌘K palette's do. Applied at the call site, so other dropdowns keep the stock cursor.
- `L2-UI-44` — Chrome gradient — every named theme paints its sidebar as a shallow tonal ramp plus one corner glow instead of a flat surface: `radial-gradient(circle at 0% 0%, --grad-glow, transparent 45%)` over `linear-gradient(160deg, --grad-top 0%, --grad-surface 30%, --grad-bottom 60%)`. The stops finish at 60% because the ramp is sized to the **viewport** (`L2-UI-46`) while the chrome occupies only the first ~60% of its 1114px gradient line; at 55/100 the sidebar showed just the top half of every ramp, which was invisible on the light palettes (0.012 L). The recipe is declared **once** in `globals.css`, against a selector list covering the live sidebar, the mobile sheet, the tinted header and the `.chrome-gradient` class the account preview tiles use; a theme opts in by declaring the three stops in its block. `default` ramps too, from stops declared beside `--background` in `:root`/`.dark` since it is the one theme that follows light/dark. `bg-sidebar` remains underneath as the flat base, so an unset variable degrades to the previous look rather than to nothing.
- `L2-UI-46` — The chrome is an L — full-height sidebar, header strip to its right — and both paint slices of **one** ramp via `background-attachment: fixed`, which makes the viewport the positioning area. Per-element gradients would restart at the seam and read as two gradients meeting at a corner. The header joins only when tinted (`L2-UI-32`) and not glass (`L2-UI-45`); the mobile sheet stays box-local, having no header beside it. Each half declares only `--grad-surface`, its own side of the chrome — **the stops, glow included, are inherited from the theme block**, so both ramp between identical colours. Re-pointing `--grad-glow` per element is what broke this last: `var(--sidebar-accent)` drops the literal's alpha and steps the seam ~5% L on every light palette, where the accent is darker than the surface. Guarded by a pixel check in `e2e/admin-chrome.spec.ts`, one palette per tone.
- `L2-UI-47` — Gradient stops are **literal colors**, never `color-mix()` over `var()`. The production CSS minifier folds such a `color-mix()` down to its first color, which silently turned the built ramp into white → surface → black while dev looked correct. Named palettes therefore spell their stops out in `globals.css` and mirror them in `CHROME_THEMES[].swatch.grad` (locked in both directions by `chrome-themes.test.ts`); `custom` derives its stops with `color-mix()` because they ship as inline style, which no build step rewrites.
- `L2-UI-45` — Glass header — opt-in, off by default, stored as `user_preference.chromeHeaderGlass` (`L2-DB-33`) and stamped as `data-chrome-glass="on"` on the shell wrapper. The header sticks to the top of the scroll container; the wash, a sheen and the blur move to a `::before` — Safari jitters with `backdrop-filter` on a `position: sticky` element, and on the header the filter's containing block would trap a non-portaled fixed descendant. The gradient image is dropped (an opaque image sits in front of the blur), via an explicit `:not([data-chrome-glass="on"])` on the gradient selector rather than a specificity race, so the ramp cannot continue across the whole strip. Instead the header **starts opaque and fades into the glass**: an `::after` paints the real ramp (same recipe, same viewport-fixed positioning — literally the sidebar's gradient continuing) under a horizontal mask that fades it out over ~340px, revealing the blurred `::before`. Seam continuity is then exact (measured +0.0% L dark, ≤1.0% light, from −1.2%/+4.3%). The mask goes on `::after`, never `::before`: a mask clips an element's `backdrop-filter` result along with its paint, so masking the blur layer punches raw unblurred page through the holes.
- `L2-UI-49` — Glass filter chains are **backdrop colour correction**, keyed on tone × app mode. The composite is `α·wash + (1−α)·filter(backdrop)`; a named palette's tone is fixed (`L2-UI-29`) while the canvas follows light/dark, so there are four cases. Same polarity (dark palette in dark mode, light in light, and any untinted header) needs only `brightness()`. Opposite polarity cannot use it — pulling a white canvas to 0.13 needs `brightness(0.14)`, which scales content variation by the same factor into a flat grey, and `contrast()` pivots on 0.5 and clips — so those use `grayscale(1) invert(…)`, the only op that moves the mean across without crushing variance: the page supplies luminance texture, the palette supplies hue. Alpha is 0.80 throughout (0.72 left blurred text ~0.10 L off and patchy; past ~0.85 modulation drops under 0.02 L and stops reading as glass), and each palette's wash pre-compensates chroma by ÷0.8 because a neutral backdrop dilutes it by exactly (1−α). Selected by `data-chrome-tone`, stamped by the layout from the catalog's `group` (and from luminance for `custom`) — never a hand-kept list of palette ids. `default` carries no tone and takes the stock chain. No `backdrop-filter` support, `prefers-reduced-transparency: reduce`, or print → solid header colour, pinning kept.
- `L2-UI-48` — Build-loop pitch — the product's shortest self-description, as a four-prompt transcript (`clone …` / `set up and run this project locally` / `create a user for me and give me the login URL` / `build feature <...>`) between the line "You have Docker and dev tools ready." and "That's how you start a project now." The prompt strings live once, in `apps/web/app/_components/build-loop.tsx`, and are exported so the copy cannot drift between surfaces. Mounted on **both** surfaces (`L1-ARCH-01`): the public homepage directly under the hero as `BuildLoop` (its own section, eyebrow + heading + card), and the admin Overview as `BuildLoopTranscript compact` inside a card above the info cards. `README.md` carries the same four lines as a fenced block under the tagline. Rendered as flat type on a card, never as a terminal mock — no window chrome, no traffic lights.
- `L2-UI-50` — Chrome **controls** take `--chrome-header-input`, not the seam colour. `--chrome-header-border` is deliberately a hairline (≈0.045 L from its surface, `L2-UI-29`) so the sidebar↔header seam reads as one surface; the header subtree re-points `--border` *and* used to re-point `--input` to it, which left the ⌘K jump control outlined at ~1.05:1 against the header — invisible on the dark palettes. Each palette now declares a separate `--chrome-header-input` (~0.28 L from the surface on dark, ~0.26 below it on light, landing both tones near 2.3:1), the header subtree points `--input` at it, and `header-search.tsx` asks for `border-input`. Stock chrome takes `--stock-input`. Still under the 3:1 WCAG non-text threshold — a deliberate stop, since a control whose label is legible on its own does not carry the boundary alone.
- `L2-UI-51` — Header type matches the sidebar: the breadcrumb trail and the Docs link are `text-[13px]`, the same size `app-sidebar.tsx` gives its menu items, so the two halves of the chrome read as one navigation surface rather than two scales.
- `L2-UI-28` — Server action `saveChromeTheme(theme)` (`account/_actions.ts`) — self-scoped to the session user, refuses ids outside the catalog, revalidates the `/backflip` **layout** (not just the page) so the shell re-renders.

## Schemas
- `L2-UI-26` — Chrome theme catalog (`apps/web/app/_lib/theme/chrome-themes.ts`): `default` plus fixed palettes — dark `slate` | `graphite` | `pine` | `aubergine`, light `gold` | `sky-blue` | `sage` | `rose-gold`. Each entry carries `id`, `label`, `group`, swatch colors for the picker and the three gradient stops (`L2-UI-44`, `L2-UI-47`). Hover/active rows sit ~0.085 L from the surface on the dark palettes and ~0.075 L **below** it on the light ones — the earlier 0.04 was too faint to find, and the stock sidebar's 0.015 was the faintest of all. Ids are the single source of truth: every named id has a matching `[data-chrome-theme="<id>"]` block in `globals.css`, and every such block has a catalog entry (locked by `chrome-themes.test.ts`). Stored per user in `user_preference.chromeTheme` as free text; `resolveChromeTheme()` narrows anything unknown back to `default`. `custom` (`L2-UI-33`) is a valid id but deliberately absent from the catalog array — it has no fixed swatch and renders as its own card.
- `L2-UI-06` — shadcn config (`packages/ui/components.json`): style `base-mira`, baseColor `neutral`, RSC on, icons `remixicon`, css vars on.
- `L2-UI-07` — Aliases: components/ui → `@workspace/ui/components`, utils → `@workspace/ui/lib/utils`.
- `L2-UI-41` — Clause titles strip the concern kind-tag (`_(iface)_`, `_(inv)_`, …) before deriving a title, so a concern-grouped contract lists real clause text rather than its tag. (`parse-docs.ts`)
- `L2-UI-21` — Docs index built at **build time**, never at runtime: a `server-only` module parses `/docs/**/*.md` (headings, `L[123]-<CAT>-<NN>` IDs, `Implements L1:` / `Depends on L2:` / inline `L2-…` cite edges) and greps `@spec` tags across `apps/*`, `packages/*`, `devops/*` into one serializable index. `yarn workspace web docs:index` writes `docs-index.generated.json`; the workspace `build` script runs it before `next build`. Rationale: the Docker runner ships only `.next/standalone`, so `/docs` is absent at runtime. Dev reads the working tree live.

## Invariants
- `L2-UI-08` — One theme source: `packages/ui`. No per-app component copies.
- `L2-UI-09` — Overlay components (tooltip/toast) require their providers mounted in root layout.
- `L2-UI-10` — Web app transpiles `@workspace/ui` (`next.config.ts transpilePackages`).
- `L2-UI-14` — `Button` infers base-ui `nativeButton` from its `render` element: `<button>` → true, any other element → false. Explicit `nativeButton` overrides. Link-buttons (`render={<a/>}` / `render={<Link/>}`) need no extra prop.
- `L2-UI-15` — Shell containers hosting page content are shrinkable (`min-w-0`), so page content never forces the shell wider than its slot.
- `L2-UI-22` — Docs explorer is read-only. No doc editing or writing from the admin UI.
- `L2-UI-29` — Named chrome themes are **fixed palettes**: they do not follow the light/dark toggle, so a platform keeps its identity in either mode. Only `default` follows the mode. Chroma is held ≤ 0.10 on the dark surfaces and ≤ 0.03 on the light ones — enough hue separation to identify a platform at a glance, never a saturated surface. Aubergine sits at the top of that range deliberately: below ~0.08 a plum reads as grey-violet rather than as a colour. Eight named palettes: four dark, four light. Chrome borders sit ≈0.045 L from their own surface: sidebar and header share one tint, so their seam is a hairline rather than a rule. One border color for the whole chrome — the sidebar's right edge and the header's bottom edge are the same value in every palette.
- `L2-UI-34` — One stylesheet serves both surfaces (`L2-UI-03`), so every chrome-theme rule gates itself on `[data-chrome-theme]` — an attribute stamped only by the admin shell. No admin chrome rule may apply to a public page, including rules keyed on a `data-slot` a public component could also use.
- `L2-UI-30` — Chrome theming is per user and cosmetic only. It changes no capability, is never used to signal environment or permission state, and an unknown stored id degrades to `default` rather than an unstyled shell.
- `L2-UI-23` — Drift badges are derived on read, never stored: `orphan` = ID no L3 note cites (L1: no L2 implements), `no code` = ID with zero `@spec` references, `needs confirm` = clause carrying the confirmation marker **outside inline code** (a doc quoting the marker while describing this rule is not drift), `broken ref` = cites an ID defined nowhere in `/docs`. The landing view lists every badge with its count and a one-line meaning, zeros included, so the pills on the rows are always legible.
